# AGENTS.md — maxclient

Инструкция для ИИ-агентов и разработчиков. Язык общения с владельцем — русский, ответы по делу и коротко.

## Что это

Веб-клиент мессенджера MAX (OneMe) на Flask. `bridge.py` держит TCP/TLS-сессию с серверами MAX и отдаёт интерфейс в браузер. Работает локально (`127.0.0.1:8080`, Termux на телефоне, десктоп) и внутри Android-обёртки (Chaquopy).

Два интерфейса:
- **классический** — `static/index.html`, один файл (стили, темы, вся логика);
- **новый `/tg/`** — собранный Telegram Web K (`static/tg/`) с мостом к протоколу MAX и своим слоем `static/tg/mx-ui.js`.

## Эталон протокола — Komet

Источник истины по опкодам, форматам пакетов и поведению клиента: **https://github.com/KometTeam/Komet** (Flutter-клиент MAX). Пользователь называет его «komet».

- Клонировать рядом (`git clone --depth 1 https://github.com/KometTeam/Komet.git`), иногда делать `git pull`. В репозиторий maxclient он не попадает (`Komet-main` в `.gitignore`).
- Опкоды: `lib/core/protocol/opcode_map.dart`.
- Запросы по областям: `lib/backend/modules/*` (например `account/sessions_module.dart`: 96 — список сеансов, 97 — завершить остальные).
- Внутренние ссылки `max.ru/:…`: `lib/frontend/widgets/max_route_handler.dart`, `lib/core/links/deep_link_service.dart`.
- Правило: **не угадывать формат запроса.** Сначала найти тот же вызов в Komet, повторить опкод и поля `payload` один в один; если там нет — искать в дампе https://github.com/vypivshiy/mah и явно сказать, что формат не подтверждён.
- Дизайн профиля и экранов настроек сверять со скриншотами Komet/Telegram, которые присылает владелец.

## Структура репозитория

- `bridge.py` — всё серверное: `MaxClient` (сокет, `send`, `send_wait`, `recv_packet`), WebSocket `/relay`, REST `/api/*`, `fetch_once()`, push (FCM), каталог устройств, скам-проверка, боты (`bots.json`).
- `static/index.html` — классический UI.
- `static/tg/` — новый UI. `index.worker-*.js` (воркер Web K с мостом `__mx*`, **минифицирован**), `mx-ui.js` (наши экраны и скин, читаемый код), `index.html`.
- `sw.js` — service worker, кеш статики.
- `android/` — Gradle-проект; Python и статика кладутся в Chaquopy через `scripts/sync-android-python.sh` (источник правды — корневой `bridge.py` и `static/*`).
- `scripts/` — `apply-patch.sh`, `generate-ota-manifest.sh` (OTA/hotpatch без пересборки APK), `tg/` (скрипты, которыми собирался `/tg/`).
- `.github/workflows/` — сборка APK и релизов.

## Как устроена связь с MAX

```
браузер /tg/ → воркер (__mxCall, очередь, op → seq) → WS /relay → bridge → MaxClient → MAX
```

- Пакет: `opcode`, `seq`, `cmd`, `payload`. Ответ на запрос приходит с тем же `seq`; `cmd == 256` — успех, иначе ошибка (смотреть `payload.error`, `localizedMessage`).
- После подключения сессия MAX становится ONLINE только после **`op 19`** (синхронизация/вход по токену). Любой другой запрос до этого получает `proto.state: Must be ONLINE session`. Воркер должен отправлять `op 19` первым после каждого (пере)подключения.
- **Не открывать вторую сессию с тем же токеном и deviceId, пока жива relay-сессия.** Сервер может сбросить рабочую. Для разовых запросов из REST использовать открытую сессию: `client.send_wait(opcode, payload)` / `_op_via_session()`; `fetch_once()` — только запасной путь. Ответы, которые ждёт сам bridge, `recv_loop` забирает по `seq` и не пересылает фронту.
- Таймауты воркера короткие специально; переподключение (`__mxResetWs`) создаёт новую сессию MAX — частые сбросы дают каскад таймаутов. Перед правкой таймингов смотреть логи `[relay]` и `[worker]`.
- Файлы: ссылка на скачивание запрашивается opcode 88 (подписанный URL со сроком действия), куски отдаёт `/video` с Range. Запрос Range за концом файла (416) на непервом куске — конец файла, не ошибка.

## Работа с `/tg/`

- Web K собран и минифицирован. Не переписывать бандлы целиком; точечные правки в `index.worker-*.js` делать скриптом с `assert count == 1` для каждой подстановки.
- Всё новое и заметное — в `mx-ui.js` (экраны `S.<имя>`, `open('<имя>')`, скин через `<style>`). Хелперы там же: `page`, `card`, `row`, `sec`, `hint`, `btn`, `toast`, `jget/jpost`.
- Внутренние ссылки `max.ru/:settings/...` перехватываются в `mx-ui.js` и ведут на наши экраны (таблица по Komet). Новый маршрут добавлять туда же.
- Настройки клиента лежат в `localStorage` с префиксом `maxclient_` и общие с классическим UI; тема `/tg/` — отдельный ключ `maxclient_tg_theme`.
- После правки воркера менять строку `worker build …` — по ней в консоли видно, что подхватилась новая версия. В основном профиле Chrome мешает кеш воркеров; проверять в инкогнито.
- Классы Web K (`#column-left`, `.sidebar-slider-item`, `.menu-horizontal-div`, `.input-search-input`, `body.is-left-column-shown`) взяты из бандла; перед правкой стилей убедиться, что класс существует.

## Правила работы

- Владелец работает с телефона (Termux, `git apply`). Изменения отдавать **одним файлом `.patch`** (`git diff`), не zip со скриптом. Патч должен накладываться на актуальный `HEAD` — перед созданием клонировать репозиторий заново и проверить `git apply --check`.
- После правок кода всегда отдавать итоговый файл, а не пересказ.
- Перед выдачей: `python3 -m py_compile bridge.py`; для JS — `node --check` (для воркера скопировать в `.mjs`).
- Не собирать APK. Сборку запускает владелец (GitHub Actions). Две версии: «MaxClient» (`com.suscersal.maxclient`) и «MaxClient FCM» (`ru.oneme.app`, ставится вместо оригинала). Правки `static/` и `bridge.py` должны доходить до устройства через OTA, без пересборки.
- Честно писать, что проверено, а что нет: у агента нет живого аккаунта MAX, UI в браузере не запускается.
- Не придумывать функции и поля протокола. Если формат неизвестен — искать в Komet, иначе спросить.
- Комментарии в коде короткие и по делу, объясняют «почему», а не «что».
- Не коммитить секреты и личные данные: `session.json`, `session.key`, `*.jks`, токены, реальные ID и тексты сообщений из запросов. В тестах только синтетические данные.
- Не перезаписывать `README.md` и пользовательские настройки (`bots.json`, `push_subscriptions.json`) без просьбы.

## Звонки (по Komet)

**Реализовано:** аудиозвонок 1:1 — исходящий (op 78) и входящий (push 137), отклонение, mute, перезвон из истории (op 79 уже была). Код: блок «Звонки» в `bridge.py` (`/api/call/start`, SSE `/api/call/events`, мост `/call-ws` к `ws2`, декодер `vcp`) и `static/calls.js` (WebRTC + экран звонка; подключён в классическом UI и в `/tg/`). Кнопки: шапка диалога и строки истории (классика), плитка «Звонок» в профиле (`/tg/`). `calls.js` добавлен в `sync-android-python.sh` и `HOT_FILES` OTA.
**Не реализовано:** группы и конференции (topology `SERVER`, SFU, data-каналы), вход по ссылке `joincall`, камера и демонстрация экрана, переподключение `ws2`. В Android-обёртке микрофон запрашивается через `WebChromeClient.onPermissionRequest` в `MainActivity.kt` (только `127.0.0.1`/`localhost`, только аудио); изменение Kotlin требует пересборки APK.
**Не подтверждено живым аккаунтом:** значение `capabilities`, формат отмены входящего (сейчас эвристика по записи `CALL` в push 128), обработка `hungup` собеседника — взято из Komet как есть.

Ниже — описание протокола из Komet.

Источник: `lib/backend/modules/calls.dart`, `lib/core/calls/*` в Komet. Звонок состоит из трёх слоёв:

1. **Сессия MAX** (та же, что у bridge): 78 — начать звонок (`conversationId` uuid, `calleeIds`, `isVideo`, `internalParams`), 76 — создать конференцию, 84 — ссылка, 166 — войти по ссылке, 195 — участники, 79 — история, 164 — удалить историю, 103 — входящие, пуш 137 — входящий звонок (`conversationId`, `vcp`). Звонок в чате — вложение `CALL`.
2. **Сигнализация `ws2`** — отдельный WebSocket. URL берётся из `endpoint` ответа 78/166 (токен уже внутри) или из `vcp` пуша 137; дописываются `version=5`, `capabilities`, `clientType=ONE_ME`, `tgt=start` (без него звонок не поднимается). Кадры JSON: `command` + `sequence` → `response`; пуши `notification`. Команды: `accept-call`, `hangup`, `transmit-data` (SDP и ICE), `change-media-settings`, `switch-topology`, `allocate-consumer`, `accept-producer`. Уведомления: `connection`, `accepted-call`, `transmitted-data`, `topology-changed`, `producer-updated`, `participant-*`, `hungup`, `closed-conversation`.
3. **Медиа** — WebRTC (unified-plan, max-bundle), ICE-серверы из `vcp`, звук Opus; для конференций SFU с data-каналами.

`vcp` — строка `<длина>:<base64(LZ4)>`, распаковывается Rust-ядром Komet; в Python/JS её надо писать заново. Если нет «connection» за 10 с после подключения к `ws2` — токен просрочен или конференция закрыта.

Порядок внедрения: история звонков (79/164) → вход в конференцию по ссылке → звонок 1:1. Сначала сверять поля с Komet.

## Ссылки `max.ru/:…`

Таблица маршрутов Komet — `lib/frontend/widgets/max_route_handler.dart` (`openMaxRoute`). В `/tg/` разбор ссылок и соответствие нашим экранам лежат в `mx-ui.js` (блок «внутренние ссылки MAX»). Новый экран → добавить маршрут туда же.

## Известные особенности

- `[WS-2] handleError` в консоли каждые 10 с — встроенный MTProto-транспорт Web K стучится в несуществующий эндпоинт; не относится к MAX.
- Нет данных по историям/реакциям/стикерам в `/tg/` — часто это ответ MAX без поля, а не баг отрисовки; проверять сырой пакет в логах воркера.
- Скрытый экран списка чатов не должен ловить тапы под открытыми вкладками сайдбара — это закрыто CSS в `mx-ui.js`, не откатывать.

## Мини-приложения ботов (по Komet)

Источник: `lib/backend/modules/webapp.dart`, `lib/frontend/screens/webapp/web_app_bridge.dart`, `chat_screen.dart` в Komet.

- Запуск: opcode 160 `{botId, startParam?, chatId?}` → `url` (`/api/web-app-init`). В `/tg/` его вызывают `messages.requestWebView` / `requestSimpleWebView` / `requestMainWebView` в `index.worker-*.js`. Окно рисует сам Web K.
- Кнопка меню бота (`bot_info.menu_button` у `users.getFullUser`) показывается, только если в `options` контакта или чата есть `HAS_WEBAPP` / `HAS_WEB_APP` / `WEBAPP` (как `hasMiniAppOption` в Komet).
- Мост событий — блок «мост мини-приложений MAX» в `static/tg/mx-ui.js`: телефон (opcode 106, `/api/web-app-phone`), поделиться, ссылки, скачивание, тактильный отклик, launch_context, viewport, NFC. Всё, что отдаёт данные наружу или открывает что-то на устройстве, — только после подтверждения пользователя (в Komet это «жест» + диалог, у нас жест внутри чужого iframe не виден).
- **Не подтверждено живым мини-приложением:** формат сообщений iframe → родитель и имена ответных событий. Не перенесено из Komet: выбор чата для `WebAppMaxShare` (текст уходит в буфер), QR-сканер, Mobile ID, биометрия «по умолчанию разрешена» (у Web K своя реализация; настоящей биометрии в браузере нет).
- Сайты внутри приложения (как `web_app_screen.dart` в Komet): ссылки из мини-приложения (`web_app_open_link`, `web_app_open_max_link`) после подтверждения открываются во встроенном браузере APK (`AndroidInAppBrowser.open`, диалог с отдельным WebView без JS-мостов и без разрешений); в обычном браузере — новая вкладка. Переходы внутри iframe мини-приложения не уводятся в системный браузер.
- Перехват `externalCallback=1` (Цифровой ID): `shouldOverrideUrlLoading` в `MainActivity.kt` (iframe и встроенный браузер) → `window.__mxExternalCallback(url)` в `mx-ui.js` → `/api/external-callback` (opcode 105 `{url}` → `{botId, startParam}` → opcode 160) → окно мини-приложения перезагружается новым адресом (если окна нет — наш оверлей). **Не проверено:** вызывает ли Android `shouldOverrideUrlLoading` для навигации внутри iframe; Kotlin-код не компилировался. Возврат из внешнего браузера по ссылке `max.ru/...?externalCallback=1` не ловится: у APK нет intent-фильтра на max.ru.

## Уведомление о новой версии (как в roblox-studio-web)

`/api/update-check` (bridge.py) сравнивает `versionCode` установленного APK с самым новым **stable**-релизом на GitHub (не draft/prerelease: hot-релизы ставятся сами через OtaUpdater). Номер берётся из названия релиза «MAX Client <tag> (v1.N)», иначе из тега `build-N`. Ответ кэшируется на 10 минут (лимит GitHub API для анонимных запросов). В `/tg/` (`mx-ui.js`) через 6 с после запуска показывается окно «Вышла новая версия» с кнопками «Перейти» (страница релиза) и «Позже»; один раз за сессию. На десктопе `versionCode` нет — уведомления нет.

## Навигация «Назад» в /tg/ и самопроверка

Системная «Назад» (Android) = `webView.goBack()`, поэтому всё, что перекрывает интерфейс (экран MAX, всплывающее меню, окно «новая версия», оверлей мини-приложения, экран звонка), **обязано быть слоем** в `mx-ui.js` (`layerPush` / `window.__mxBackLayer`), иначе «Назад» уйдёт по истории Web K слишком глубоко (закроет чат под оверлеем и т.п.). Экран звонка (`calls.js`) ставит слой-охрану, который поглощает «Назад» до завершения звонка.

Проверка: «Настройки → … → Отладка → Проверка навигации» (`window.__mxNavSelfTest()`): открывает все экраны MAX, жмёт «Назад» нативным `history.back` и сверяет слои, DOM и глубину истории; отчёт можно скопировать. Касания и свайпы внутри самого Web K (чаты, шторки) она не проверяет. Новый оверлей = новый слой + строка в самопроверке.
